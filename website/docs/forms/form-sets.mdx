# 🧱 Form sets and layouts

Edit views are laid out with a small composition API in `content_studio.form`.
Leave `edit_main` unset and the editor renders the model's fields in
declaration order; set it and you control the layout.

```python
from content_studio.form import Field, FieldLayout, FormSet


@register(Article)
class ArticleStudio(ModelStudio):
    edit_main = [
        FormSet(
            title="Content",
            description="The article itself",
            fields=[
                "title",
                Field("status", col_span=1),
                Field("body", col_span=3),
            ],
        ),
    ]
    edit_sidebar = ["published_at", "rating"]
```

## Building blocks

- **`Field(name, col_span=1, label=None, readonly=False, widget=None)`** — one
  model field. Strings are shorthand for `Field(name)`.
- **`FieldLayout(fields=[...], columns=1)`** — a field group rendered in `columns`
  columns.
- **`FormSet(title, description, fields)`** — a titled block of fields; the
  primary grouping in the main area.
- **`FormSetGroup(label, formsets=[...])`** — groups form sets; a list of form
  sets is wrapped automatically.

A list of plain fields is wrapped in a form set automatically, and a list of
form sets in a group — so simple layouts stay simple.

:::caution
Every required model field must appear in `edit_main` or `edit_sidebar` —
the editor only submits the fields it shows, so a required field left out
(including through `exclude`) fails validation on save. Missing fields are
reported by the `content_studio.W001` system check (`manage.py check`,
see [System checks](/docs/system-checks)).
Fields with a default, nullable fields and blank fields are never required,
and neither are the fields Content Studio fills itself (the created/edited
stamps and the tenant relation).
:::

## Sidebar

`edit_sidebar` works the same way and renders in the narrower sidebar
column. Fields set as `readonly` display their value without an input.

A field's editing widget can be overridden per field by passing a widget
class: `Field("summary", widget=widgets.TextAreaWidget)`. See
[Widgets](/docs/forms/widgets) for the available widgets.

## Components

Edit views can carry components — interactive ones like links and
buttons, and display ones like the activity log.

```python
from content_studio.form import ActivityLog, ButtonLink


class ViewSiteLink(ButtonLink):
    component_type = "LinkButton"
    label = "View on site"
    icon = "external-link"
    copy = False

    def get_url(self, obj, request):
        return obj.get_absolute_url()


@register(Article)
class ArticleStudio(ModelStudio):
    edit_sidebar = ["published_at", "author", ViewSiteLink(), ActivityLog()]
```

The shipped `ActivityLog` component renders the object's recorded
history under an optional, translated title (defaulting to
"Activity"); it needs no request handling — the entries come from
the generated API's activity endpoint.

Subclass `Component` for fully custom behavior: implement `handle_request(obj,
request)` and the component gets its own endpoint. Components are looked
up by ID, and IDs derive deterministically from the class and its
`get_id_parts()` — pass an explicit `component_id` (a UUID) when two
components of the same class share a label.
