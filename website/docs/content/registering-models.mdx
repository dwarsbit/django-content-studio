# 📋 Registering models

A model appears in the admin once you register it with a studio: a
`ModelStudio` subclass that configures its list page and edit page. Put the
registrations in your app's `admin.py`, where Content Studio looks for them.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
```

`@register` also takes several models at once, which then share the studio:
`@register(Category, LandingPage)`.

Registrations go to the site set in the
[`ADMIN_SITE`](/docs/settings#admin_site) setting. Content Studio keeps its
own registry: models registered only with the classic Django admin do not
appear in the admin. The user model is the exception. It is registered with
a default studio, so editors can manage users from the start; register your
own studio for it to change how it looks.

## Studio options

| Option | Effect |
|--------|--------|
| `table_display` | The columns of the table view |
| `list_filter` | The fields editors can filter on |
| `search_fields` | The fields the search box searches |
| `sortable_by` | The columns editors can sort on |
| `ordering` | The default sort order of the list page |
| `list_per_page` | The number of objects per page (default `20`) |
| `list_description` | A description below the model's name on the list page |
| `soft_delete` | The field that marks objects as trashed (see [below](#soft-delete-and-the-trash)) |
| `reorder_field` | The field editors reorder objects by (see [below](#reordering)) |
| `icon` | The model's icon in the main menu, such as `"ph-bold ph-article"` |

When `ordering` is not set, objects are sorted by primary key, so pages stay
stable.

Icons come from the bold weight of [Phosphor](https://phosphoricons.com):
write `ph-bold ph-` followed by the icon's name. The same goes for every
`icon` option in Content Studio.

## Singletons

For a model with exactly one object, such as site settings, set
`is_singleton` on the studio:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import SiteSettings


@register(SiteSettings)
class SiteSettingsStudio(ModelStudio):
    is_singleton = True
    edit_main = ["site_name", "tagline"]
```

A singleton has no list page: the menu opens its edit page directly. Editors
can create the object only while none exists, and cannot delete it. Models
built on the built-in `SingletonModel` are treated as singletons without the
option.

## Inlines

Inlines edit related objects on the parent's edit page, such as the reviews
of an article. Declare an inline studio and add it to the parent's studio:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import InlineModelStudio, ModelStudio

from .models import Article, Review


class ReviewInline(InlineModelStudio):
    model = Review
    table_display = ["text", "stars"]


@register(Article)
class ArticleStudio(ModelStudio):
    inlines = [ReviewInline]
```

When the inline model has more than one foreign key to the parent, name the
one to use with `fk_name`. The inline's `table_display` sets its columns.
Inline objects only exist within their parent: editors can only add them to
parents they may view.

## How related objects appear

Wherever an object shows up as a related object (in a picker, in a column or
as a selected value) the related model's studio decides how it looks, with
`get_relation_display`. By default it shows the object's string
representation.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio, RelationDisplay

from .models import Category


@register(Category)
class CategoryStudio(ModelStudio):
    def get_relation_display(self, obj, request):
        return RelationDisplay(
            title=obj.name,
            description=f"{obj.article_set.count()} articles",
            icon="ph-bold ph-tag",
        )
```

`RelationDisplay` takes a `title` and, optionally:

- `description`: a second line of text;
- `icon`: a CSS icon class, like the studio's `icon`;
- `initials`: a character on a colored circle, the color derived from the
  initials;
- `avatar`: an image URL.

When several are set, the admin shows the avatar first, then the initials,
then the icon. Models without a studio always show their string
representation.

## The list page

The list page shows objects as a **table**, the default, or as a **list** of
readable items. Set the views to offer with `list_views`; with more than one,
editors switch with a toggle and the admin remembers their choice per model.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
    list_views = ["table", "list"]
    list_item_display = {
        "title": "title",
        "description": "body",
        "meta": "get_status_display",
    }
```

### Table columns

`table_display` lists the table's columns: field names, or `TableColumn`
objects for a custom header, a format or a computed value.

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.form import TableColumn
from content_studio.formats import NumberFormat

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = [
        "title",
        TableColumn(field="published_at", header="Published"),
        TableColumn(field="get_word_count", header="Words", format=NumberFormat),
    ]

    def get_word_count(self, obj, request):
        return len(obj.body.split())
```

A column's `field` is a model field or a method on the studio. A method
takes `(obj, request)` and returns a value its format can show: text for text
formats, a number for `NumberFormat`, an ISO 8601 string for the date and
time formats. Without a `format`, a method column shows text and a field
column uses its field type's format.

A column without a `header` uses the field's verbose name; a method column
without one has no header. Editors can only sort on columns backed by a model
field.

`list_display`, the classic Django admin's name for the table columns, also
works, so a studio ported from the classic Django admin keeps its columns.
System check `content_studio.W010` asks you to rename it to `table_display`;
when both are set, `table_display` applies.

### List items

`list_item_display` maps the parts of a list item to field or method names:
a prominent `title`, a muted `description` and a `meta` label on the right.
For items computed in code, override `get_list_item_display` instead:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ListItemDisplay, ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    list_views = ["table", "list"]

    def get_list_item_display(self, obj, request):
        return ListItemDisplay(
            title=obj.title, description=obj.author.get_full_name(), meta=obj.status
        )
```

## Bulk actions

In the table view, editors select objects (the header checkbox selects the
whole page) and run an action from the bar that appears. A selection belongs
to one page: paging, filtering or sorting clears it.

The built-in delete action is available to editors with delete permission.
Add your own actions to the studio with `@bulk_action`; like the actions of
the classic Django admin, they receive the request and the selected objects
as a queryset:

```python
# blog/admin.py
from content_studio import register
from content_studio.actions import bulk_action
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    @bulk_action(
        label="Publish",
        icon="ph-bold ph-paper-plane-tilt",
        confirm="Publish the selected articles?",
        allowed_permissions=["change"],
    )
    def publish(self, request, queryset):
        count = queryset.update(status=Article.Status.PUBLISHED)
        return f"Published {count} articles."
```

- `label`: the action's name; by default, the method name.
- `icon`: an icon class, like the studio's `icon`.
- `confirm`: a question to confirm before the action runs.
- `allowed_permissions`: the model permissions that allow the action; any one
  of them is enough. Without it, everyone who can see the list can run the
  action.

The return value is the message editors see: a number reports how many
objects changed, a string is shown as it is.

The built-in actions record every object they change in its history. Your
own actions record nothing by themselves. To record a change, call
`record_change` for each object, with `"created"`, `"updated"`,
`"deleted"`, `"restored"` or `"reordered"` and an optional message. Record a
deletion before you delete the object:

```python
# blog/admin.py
from content_studio import register
from content_studio.actions import bulk_action
from content_studio.admin import ModelStudio
from content_studio.signals import record_change

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    @bulk_action(label="Publish", allowed_permissions=["change"])
    def publish(self, request, queryset):
        articles = list(queryset)
        queryset.update(status=Article.Status.PUBLISHED)

        for article in articles:
            record_change(request, article, "updated", "Published.")

        return len(articles)
```

The studio's `actions` attribute chooses which actions are offered:

```python
actions = None                   # the default: delete and every @bulk_action
actions = []                     # no bulk actions
actions = ["publish", "delete"]  # exactly these, in this order
```

System check `content_studio.E007` reports unknown or duplicate names and
an action that would replace the built-in delete.

## Soft delete and the trash

By default, deleting an object removes it from the database. To move
objects to a trash instead, set `soft_delete` to a nullable date or date and
time field on the model that marks an object as trashed:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    soft_delete = "removed_at"
```

With the option set:

- deleting fills in the field instead of removing the object, and the object
  disappears from the list page;
- the list page links to the model's trash, where editors restore objects
  (with change permission) or delete them for good (with delete permission);
- restoring an object is recorded in its history.

Any model with such a field works; the built-in `SoftDeletableModel` has one
called `removed_at`. System check `content_studio.E008` reports a field that
is missing or of the wrong type.

## Reordering

To let editors put objects in their own order, add a number field to the
model and name it in `reorder_field`. The list page then follows that
order, and every row gets a handle to drag it to another position:

```python
# blog/models.py
from django.db import models


class Category(models.Model):
    name = models.CharField(max_length=50)
    position = models.PositiveIntegerField(default=0)

    def __str__(self):
        return self.name
```

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Category


@register(Category)
class CategoryStudio(ModelStudio):
    table_display = ["name"]
    reorder_field = "position"
```

With the option set:

- the table view and the list view show a drag handle on every row; editors
  drag rows with the pointer, or focus the handle and move the row with the
  keyboard (space to pick it up, the arrow keys to move it, space to drop
  it);
- each row's menu moves the object one step up or down, or to the top or
  the bottom of the list, also when that is on another page. A step up or
  down passes the neighboring object of the list as currently filtered;
- reordering needs change permission, and every move is recorded in the
  object's history;
- reordering is off while editors sort by a column or search, because then
  the list does not show the manual order. Filtering keeps it on.

Content Studio only rewrites the positions of the objects between the old
and the new place, in one update query: the model's `save()` method and
its signals do not run for a move. Existing gaps between positions stay. When several
objects share a position, such as `0` for every existing row after you add
the field, Content Studio numbers the list from `1` on the first move. If
you set `ordering` yourself, start it with the reorder field; system check
`content_studio.W013` warns when it does not.

### Reordering per group

When objects are ordered within a group, such as reviews per article, list
the fields that form the group in `reorder_scope`. Objects then move among
the objects that share those values:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Review


@register(Review)
class ReviewStudio(ModelStudio):
    table_display = ["text", "article"]
    list_filter = ["article"]
    reorder_field = "position"
    reorder_scope = ["article"]
```

Filter the list by the group to see one order at a time. Inlines are always
ordered per parent, so an inline needs only `reorder_field`:

```python
# blog/admin.py
from content_studio.admin import InlineModelStudio

from .models import Review


class ReviewInline(InlineModelStudio):
    model = Review
    table_display = ["text", "stars"]
    reorder_field = "position"
```

On a model with a tenant field, objects are ordered per tenant (see
[Multi-tenancy](/docs/multi-tenancy)).

### Your own ordering implementation

The built-in reordering works with a number field. If your model keeps its
order some other way, such as with django-ordered-model, override
`reorder` on the studio. It receives the object and either `after` or
`before`: the object to place it next to. Name the field the list is sorted
by in `reorder_field`:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio

from .models import Category


@register(Category)
class CategoryStudio(ModelStudio):
    reorder_field = "order"

    def reorder(self, request, obj, *, after=None, before=None):
        if after is not None:
            obj.below(after)
        else:
            obj.above(before)
```

Return `False` from `reorder` when nothing moved, so no change is recorded.

The built-in `ManualOrderModel` has an `order_key` field to use as the
reorder field, and its `reorder()` method numbers the order keys from `1`
again. Set `order_scope` on the model to the fields that form a group, like
`reorder_scope`.

System check `content_studio.E017` reports a reorder field that is missing
or, without your own `reorder`, not a number field, and `reorder_scope`
entries that are not model fields.

## Object history

The `ActivityLog` component shows an object's history on its edit page: every
addition, change and deletion, newest first. Add it to the sidebar or to any
form set:

```python
# blog/admin.py
from content_studio import register
from content_studio.admin import ModelStudio
from content_studio.form import ActivityLog, FormSet

from .models import Article


@register(Article)
class ArticleStudio(ModelStudio):
    edit_sidebar = [
        FormSet(fields=["published_at", "author"]),
        FormSet(fields=[ActivityLog(title="History")]),
    ]
```

The title is "Activity" unless you pass one. The history appears on the edit
page of saved objects only, for editors who may view the object. Each
`FormSet` in the sidebar is its own card, so the history above gets a card of
its own.

## Use your own site

The default site, `content_studio.admin.admin_site`, is enough for many
projects. To add a dashboard, model groups or extensions, subclass
`ContentStudioSite` in a module of its own, so your `admin.py` modules can
import it:

```python
# mysite/studio.py
from content_studio.admin import ContentStudioSite


class BlogStudioSite(ContentStudioSite):
    pass


admin_site = BlogStudioSite()
```

```python
# mysite/settings.py
CONTENT_STUDIO = {
    "ADMIN_SITE": "mysite.studio.admin_site",
}
```
