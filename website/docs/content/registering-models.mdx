# 📋 Registering models

Models are registered with the `@register` decorator on a `ModelStudio`
subclass:

```python
from content_studio import register
from content_studio.admin import ModelStudio


@register(Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
```

`@register` accepts multiple models, and registrations go to the Content
Studio site configured in `CONTENT_STUDIO["ADMIN_SITE"]`:

```python
@register(Article, Category)
class SharedStudio(ModelStudio):
    pass
```

:::note
`register` is exposed lazily: `from content_studio import register` works
anywhere in your code, without importing the studio machinery before
Django is ready.
:::

## Content Studio owns its registry

Content Studio keeps its own registry — it does not read the Django
admin's global registry. Models registered only with the classic Django
admin do not appear in the studio; register each model you want to
manage with `@register`.

The one exception is the user model: it is registered automatically with
a default studio, so user management works out of the box. Register your
own studio for it to customize it.

## ModelStudio options

| Option | Effect |
|--------|--------|
| `table_display` | Columns of the table view |
| `list_filter` | Filterable fields in the list view's filter panel |
| `search_fields` | Fields searched by the search box |
| `sortable_by` | Columns the user may sort on |
| `list_per_page` | Page size (default 20) |
| `list_description` | Description below the model name on list pages |
| `ordering` | Default ordering of list views (falls back to `pk` for stable pagination) |
| `icon` | Icon shown in the main menu |

## Singletons

Settings-style models with a single row declare `is_singleton` on the
studio:

```python
@register(SiteSettings)
class SiteSettingsStudio(ModelStudio):
    is_singleton = True
    edit_main = ["site_name", "tagline"]
```

Singletons skip the list view: the single object opens directly in the
editor, creating is only allowed while no object exists, and deletion is
not offered.

:::note
As a fallback for models that carry a model-level `is_singleton` marker (for
example [Django Blueprint](/docs/blueprint-integration)'s `SingletonModel`),
that marker is honored too — a concrete *field* named `is_singleton` is
ignored.
:::

## Inlines

Related child models edit inside their parent's edit view. Declare them
with the inline class:

```python
from content_studio.admin import InlineModelStudio, ModelStudio


class ReviewInline(InlineModelStudio):
    model = Review


@register(Article)
class ArticleStudio(ModelStudio):
    inlines = [ReviewInline]
```

An inline declares its `model` and — when more than one foreign key
points at the parent — the `fk_name` of the relation. Inline rows show
the columns configured in the inline's `table_display`.

Inlines live inside their parent's edit view and stay there: inline lists are
always shown in the context of a parent, and inline objects cannot be attached
to a parent the user cannot see.

## Relation display

Wherever a related object appears — relation pickers, list views and
selected-value badges — its display is controlled by the **related model's
studio** through `get_relation_display`. The default shows the object's
string representation:

```python
from content_studio.admin import ModelStudio, RelationDisplay


@register(models.Category)
class CategoryStudio(ModelStudio):
    def get_relation_display(self, obj, request):
        return RelationDisplay(
            title=obj.name,
            description=f"{obj.article_set.count()} article(s)",
            icon="ph-bold ph-tag",
        )
```

`RelationDisplay` takes a `title` (required), a `description`, an `icon`
(a CSS class, like the `ModelStudio.icon`), `initials` (shown as one character on
a colored circle — the color is derived from the full initials value) and an
`avatar` (an image URL). Everything but the title is optional and omitted
from the interface when empty. When several glyphs are set, one is shown with
the priority: avatar, then initials, then icon. Models without a registered
studio always fall back to the string representation.

## List views

The list page can render as a **table** (the default) or as a **list** of
readable rows. Which views a model offers is declared with `list_views`;
more than one shows a toggle, and the choice persists in the URL:

```python
@register(models.Article)
class ArticleStudio(ModelStudio):
    table_display = ["title", "status", "published_at"]
    list_views = ["table", "list"]
```

The table's columns come from `table_display`. A column is a field name,
or a `TableColumn` for a custom header, an explicit format or a computed
value:

```python
from content_studio.form import TableColumn


@register(models.Article)
class ArticleStudio(ModelStudio):
    table_display = [
        "title",
        TableColumn(field="published_at", header="Published"),
        TableColumn(field="get_word_count", header="Words", format=NumberFormat),
    ]

    def get_word_count(self, obj, request):
        return len(obj.body.split())
```

`TableColumn(field=...)` references a model field or a method on the
studio. Methods take `(obj, request)` and return a JSON-safe value the
format understands: strings for text-like formats, numbers for
`NumberFormat`, ISO strings for the date and time formats. A method
column without a format renders through `TextFormat`; a field column
without one keeps its field type's default format.

Column headers fall back to the field's verbose name; method columns
without a `header` have no label. Method columns cannot be sorted —
ordering is restricted to real model fields.

The list view's rows are
configured separately through `list_display` — a mapping of roles to field
or model method names:

```python
list_display = {"title": "title", "description": "body", "meta": "get_status_display"}
```

Rows render a prominent `title`, a muted `description` and a `meta` badge.
The API ships every row's resolved display, so fully computed rows are
possible by overriding `get_list_display`:

```python
def get_list_display(self, obj, request):
    return ListDisplay(title=obj.title.upper(), description=obj.subtitle, meta=obj.status)
```

:::caution
Unlike the classic Django admin, `list_display` configures the list view —
not the table columns. Passing an old-style list is reported by the
`content_studio.E001` system check (`manage.py check`); use `table_display`
for the columns.
:::

## Configuring the site

The studio site is configured through the `CONTENT_STUDIO["ADMIN_SITE"]`
setting, which points at a `ContentStudioSite` instance. The default site
(`content_studio.admin.admin_site`) is enough for most projects; subclass
`ContentStudioSite` to add a dashboard, model groups or extensions. Put the
site instance in its own module (or above the registrations) so the
`@register` decorator can import it while your `admin.py` runs:

```python
# apps/blog/studio.py
from content_studio.admin import ContentStudioSite

admin_site = ContentStudioSite()
```

```python
# settings.py
CONTENT_STUDIO = {
    "ADMIN_SITE": "apps.blog.studio.admin_site",
}
```
